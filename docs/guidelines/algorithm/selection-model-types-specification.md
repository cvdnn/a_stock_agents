# 智能选股系统 · 模型类型设计规范 (Selection Model Types Specification)

> 文档 ID：`SPEC-ALGO-ISS-MT-001` · 上级规范：[`selection-system-specification.md`](./selection-system-specification.md)（`SPEC-ALGO-ISS-001`）§3
> 适用范围：模型类型注册中心、`condition_tree`（条件选股）、`funnel`（漏斗选股）、`scoring_rank`（评分排序）、`composite`（组合模型）四类选股模型的配置 Schema、编译规则、输出契约与扩展规则。
> 核心目标：把「模型类型」这一维度从主规范中独立出来，明确每种类型的结构契约、编译产物与首期状态，使新增类型可插件式扩展而不改动已有类型定义。
> 边界：本文只定义**类型级设计与规范**。配置模型机制（层级字段、规则元数据、三态求值、存储与版本）见主规范 §7；用户自建流程与引导式意图匹配见主规范 §3.4/§3.4.1。任何具体策略参数（如 20 日新高、高开区间）属**示例口径**，只以「示例说明」出现，不构成类型规范。

---

## 1. 设计原则

1. **类型不绑定运行引擎**：模型类型只描述结构、Schema 与编译器；所有类型必须先编译为统一的层级中间结构 `CompiledSelectionPlan`（主规范 §7.2），再由层级漏斗引擎（HFE）执行。禁止为某个类型单独实现一套运行时。
2. **统一编译、统一执行**：类型差异只保留在模型构建体验、默认模板与约束规则中；编译后一律收敛为「有序层级 + 层内表达式 + 触发器」。
3. **插件式后向兼容**：通过 `SelectionModelTypeRegistry` 注册新类型，新增模型类型不得修改已有模型定义。
4. **注册即声明契约**：每个类型必须声明配置 Schema、可用节点、编译器、调试器、Web 编辑器能力与输出契约，缺一不可发布。

---

## 2. 模型类型注册中心

平台通过 `SelectionModelTypeRegistry` 注册模型类型。首期注册 4 个类型：

| 类型 | ID | 结构 | 典型用途 | 首期状态 |
|---|---|---|---|---|
| 条件选股 | `condition_tree` | 多维度规则组 + 布尔表达式树 | 同一时点按技术面、基本面、行业面、资金面、消息面筛选 | P0 |
| 漏斗选股 | `funnel` | 多阶段逐层收缩 + 阶段触发器 | 收盘候选跨时段传递至次日开盘确认 | P0 |
| 评分排序 | `scoring_rank` | 因子评分 + 权重 + Top-K | 多因子综合评分与排名 | P2 |
| 组合模型 | `composite` | 引用其他模型输出并做集合运算 | 多模型交集、并集、排除与二次排序 | P2 |

类型到编译结果的统一映射：

| 用户侧模型类型 | 编译结果 | 统一运行方式 |
|---|---|---|
| 条件选股 | 单层或多层，每层包含安全逻辑表达式树 | 层级漏斗引擎逐层执行 |
| 漏斗选股 | 多个有序层级及阶段触发器 | 层级漏斗引擎逐层执行 |
| 评分排序 | 过滤层、评分层、排序层和输出层 | 层级漏斗引擎按节点类型执行 |
| 组合模型 | 子模型输入、集合运算层和汇总层 | 层级漏斗引擎按依赖图执行 |

**首期可运行约束**：主规范 §7.2 规定首期层级类型仅 `filter`、`gate`、`output` 可执行；`score`、`rank`、`branch`、`merge` 在对应执行器实现前只能被编译器拒绝，不得在界面显示为可运行。因此 `scoring_rank`、`composite` 首期只登记类型与 Schema，其节点在编译器与 Web 编辑器实现前**不可发布**。

## 3. `condition_tree` 条件选股模型（P0）

### 3.1 结构

条件选股由一个或多个维度组组成。首期内置维度：

- 技术面：均线、突破、量能、MACD、波动率、形态；
- 基本面：盈利、成长、估值、现金流、财务风险；
- 行业面：行业归属、行业强度、行业资金、主线排名；
- 资金面：主力净流入、北向、换手、量比、筹码；
- 消息面：公告、新闻、事件、舆情时效；
- 市场面：指数趋势、情绪、涨跌停结构；
- 风险面：ST、退市、停牌、流动性、异常交易；
- 自定义：由已注册字段和规则组成，不允许执行任意代码。

**首期数据准入标注（2026-09 裁定）**：维度注册与维度可发布是两个独立事实。本期仅下列维度可用于正式版本：

| 维度 | 首期可发布规则 | 说明 |
|---|---|---|
| 技术面 | 均线、突破、量能、MACD、波动率、形态 | 全部基于本地日K快照，可发布 |
| 市场面 | 指数趋势、涨跌停结构 | 基于指数日线，可发布 |
| 风险面 | 高股价、超高PE、长期阴跌、ST名称型排除 | 见主规范 §11.1；长期亏损与业绩差本期不可发布 |
| 基本面/行业面/资金面/消息面 | 仅注册维度，不可发布 | 财务、行业快照、资金流、公告新闻契约未建立，含相应规则的版本禁止发布或激活 |

### 3.2 逻辑表达式树

逻辑使用**安全表达式树**，不接受字符串 `eval`。支持 `AND`、`OR`、`NOT` 和嵌套分组；Web 通过可视化组块生成 AST，后端负责最终校验与执行。

条件选股本质上是层级漏斗的一种简化建模方式：简单条件模型可编译成一个过滤层，按业务维度拆分的条件模型可编译成多个顺序层。逻辑运算的叶子是原子规则，参与 `AND/OR/NOT` 求值的是规则产生的 `PASS/FAIL/UNKNOWN` 三态结果（主规范 §7.7）。

### 3.3 顺序层语义约束

顺序层级之间天然表示「通过上一层 AND 通过下一层」。类似 `(A AND B) OR (C AND D)` 的表达式必须放在同一层的嵌套逻辑树中；**首期不允许用普通顺序层表达跨层 OR**。后续如需跨层并行与合并，必须增加显式分支/合并节点，不能隐式改变候选传递语义。

### 3.4 配置结构（示例说明）

> **示例说明**：下列 Schema 为**示例样例**（案例说明，非规范），仅演示条件模型的字段组织方式；其中的组名、规则与表达式**均为示例**，不代表系统内置维度或默认模型。

```yaml
model_type: condition_tree
groups:
  - id: technical
    name: 技术面
    logic: all
    rules: []
  - id: industry
    name: 行业面
    logic: any
    rules: []
  - id: news
    name: 消息面
    logic: all
    rules: []
expression:
  op: and
  children:
    - ref: technical
    - op: or
      children:
        - ref: industry
        - ref: news
    - op: not
      child: {ref: risk}
```

## 4. `funnel` 漏斗选股模型（P0）

### 4.1 结构

漏斗选股由有序层级构成，每层接收上游候选并输出更小的候选集合。层级除规则外，还必须定义触发器：

| 触发器 | ID | 示例 |
|---|---|---|
| 固定交易时间 | `trading_time` | 每个交易日 15:35 之后（定盘数据仍需另行校验） |
| 时间窗口轮询 | `interval_window` | 09:30～09:35 每 3 秒 |
| 上游完成 | `upstream_completed` | 上一阶段成功后 |
| 数据就绪 | `data_ready` | 已取得至少 6 个分钟点 |
| 条件触发 | `condition` | 已注册谓词条件成立 |
| 事件触发 | `event` | 新公告、股池更新 |
| 手工触发 | `manual` | 用户点击调试或正式运行 |

条件触发器同样使用受限 AST 和注册字段，禁止任意 Python 表达式。

### 4.2 跨时段候选传递

漏斗类型的核心特征是**跨时段候选传递**：层与层之间可跨越交易日（如「收盘后初筛 → 次日早盘确认」）。因此每层必须显式声明 `schedule` 触发器与时点契约；候选传递不得隐式依赖 YAML 物理顺序（层级顺序由 `order` 决定）。跨时段层级的数据就绪与定盘口径遵循主规范 §5 时点契约与 §11 数据装配。

### 4.3 与条件选股的关系

「条件选股」和「漏斗选股」的区别保留在模型构建体验、默认模板和约束规则中，**不再形成两套运行时**：前者强调维度分组和逻辑树，后者强调候选传递、跨时段层级和阶段触发，二者最终都由模型编译器生成标准层级定义。

## 5. `scoring_rank` 评分排序模型（P2 · 设计态）

### 5.1 结构

评分排序模型由四类节点组成，按顺序编译为层级：

1. **过滤层**（`filter`）：与条件选股共用安全表达式树，先把不适格候选剔除；
2. **评分层**（`score`）：对每个候选按已注册因子与权重计算综合得分；
3. **排序层**（`rank`）：按得分排序并截断至 Top-K；
4. **输出层**（`output`）：产出排序候选清单及其因子明细。

### 5.2 设计约束

- 因子必须来自注册中心并携带 `parameter_schema`；权重之和与归一化口径必须在编译期校验并纳入 `plan_hash`；
- Top-K 的 `K` 与排序稳定性（并列名次的裁决规则）必须显式声明，不得依赖实现默认；
- `score`、`rank` 节点在对应执行器实现前由编译器拒绝发布；本节仅定义结构契约，落地时序以主规范 §19 模块规划为准。

## 6. `composite` 组合模型（P2 · 设计态）

### 6.1 结构

组合模型引用其他已发布模型的输出，做集合运算：

1. **子模型输入**：声明引用的子模型及其版本（冻结 `model_version`/`plan_hash`）；
2. **集合运算层**（`merge`/`branch`）：交集、并集、排除；
3. **汇总层**：二次排序或加权合并。

### 6.2 设计约束

- 子模型引用必须固定版本，禁止运行中自动升级到子模型的新活动版本；
- 集合运算按依赖图执行，须检测循环引用并在发布阶段拒绝；
- 组合模型只做集合与排序运算，**不得反向修改子模型的候选语义**；
- `branch`/`merge` 节点在实现前由编译器拒绝发布。

## 7. 统一编译契约

所有类型共享同一编译契约，规范定义见主规范 §7.2：

| 契约项 | 要求 |
|---|---|
| 编译产物 | 不可变 `CompiledSelectionPlan`，引擎只接收该结构 |
| 哈希稳定性 | 相同模型版本 + 相同编译器版本必须生成相同 `plan_hash` |
| 类型展开 | 条件模型维度组展开为层内表达式节点；漏斗层级按依赖与 `order` 编译为多个 stage；评分排序生成过滤/评分/排序/输出层；组合模型按依赖图展开 |
| 三态求值 | 层内表达式统一使用 `AND/OR/NOT` 与 `PASS/FAIL/UNKNOWN`（主规范 §7.7） |
| 跨层语义 | 普通顺序层之间只做候选传递（等价逐层 AND）；跨层 OR 需显式分支/合并节点 |
| 失败前置 | 无法解析的规则、数据集、触发器或节点类型必须在发布阶段失败，不得延迟到运行期猜测 |

---

## 8. 类型扩展与兼容规则

1. 新增类型通过 `SelectionModelTypeRegistry` 注册，声明 §1.4 的全部契约项后方可发布；
2. 新增类型**不得修改**已有类型的 Schema、编译规则与输出契约；
3. 已被引用的类型（如 `composite` 的子模型）不得改变其输出契约的语义；如需变更须走版本迁移；
4. 类型的首期状态（P0/P2）由主规范实施看板维护，未实现节点不得在界面显示为可运行。
