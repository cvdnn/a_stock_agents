# 行情数据同步文档系列整合设计

> 日期：2026-09-24  
> 状态：已确认，待实施  
> 适用范围：`SPEC-DATA-001`、`SPEC-UI-003` 及其索引与交叉引用

## 一、目标

将现有 `market-data-sync-*` 与 `data-sync-control-console-*` 明确整合为同一个“行情数据同步系统”功能系列，同时保持数据面与控制面的职责隔离：

- 数据面负责同步引擎、交易日历、SQLite 存储、完整性审计、自愈和守护进程；
- 控制面负责 Web 运行控制、任务记录、高级设置、手动操作和定时配置；
- 控制面依赖数据面，数据面不依赖 UI；两组文档互相导航，但不合并 SSOT。

## 二、文档命名与治理

控制面文档统一采用 `market-data-sync-control-console-*` 前缀：

- `data-sync-control-console-specification.md` 重命名为 `market-data-sync-control-console-specification.md`；
- `data-sync-control-console-plan.md` 重命名为 `market-data-sync-control-console-plan.md`。

规范编号保持不变：数据面继续使用 `SPEC-DATA-001`，控制面继续使用 `SPEC-UI-003`。所有总索引、分类索引、交叉链接和正文引用同步更新。

## 三、P3 全市场同步契约

### 3.1 自动同步

- 仅在交易日运行，默认时间为 `16:00`，允许通过 `HH:MM` 配置；
- 自动任务固定使用增量模式，非交易日跳过；
- 默认批次大小为 600、并发数为 8；
- 同一时刻最多运行一个 P3 任务；
- P0/P1 任务优先，P3 不得抢占持仓或自选同步任务；
- P3 局部失败不得改变已经完成的 P0/P1 结果。

### 3.2 控制台手动操作

- 范围支持全市场、沪市、深市、北交所和用户选择的股票代码；
- 支持增量同步、完整性审计和缺漏修复；
- 全量重建属于高负载操作，提交前必须展示影响范围并二次确认；
- 存在冲突的活动 P3 任务时，禁止重复提交。

### 3.3 任务契约

新任务统一使用以下规范字段：

```text
task_type = data_sync
tier = P3
trigger = scheduled | manual
scope = full_market | sh | sz | bj | selected
mode = incremental | full | audit | repair
```

任务进度至少包含总标的数、已处理数、成功数、失败数、当前批次和预计剩余量。`sync` 仅作为历史任务的兼容别名，不再用于创建新任务。

## 四、配置语义

原“数据源优先级”拆分为两个配置域：

1. 外部行情源优先级：腾讯、新浪、东方财富；
2. 本地数据层：SQLite 路径、WAL 状态、本地优先读取策略和缓存回源策略。

SQLite 是本地存储与离线读取层，不得与外部行情供应商一起排序。

P3 设置包括启用开关、自动执行时间、并发数、批次大小、失败重试次数，以及手动全量同步的权限与确认要求。

## 五、术语与实施状态

- P0–P3 只表示同步标的优先级；
- `SPEC-DATA-001` 的实施阶段改用 M1–M4，避免术语重载；
- `SPEC-DATA-001` 保持现有核心数据能力“正式基线”状态；
- `SPEC-UI-003` 继续标记为 RFC；
- 已有 UI 能力只有在代码证据充分时才可标记完成或部分完成；
- API、设置服务和 P3 定时调度等未实现能力必须保持待实施状态；
- P3 自动调度是目标契约，由 `SPEC-UI-003` 跟踪落地，不得写成 `SPEC-DATA-001` 已交付能力。

## 六、本轮实施边界

本轮只修改规范、实施计划、文件命名、索引和交叉引用，不实现尚处 RFC 阶段的前端、服务端或守护进程代码。

## 七、验收标准

- 全仓库不再引用旧控制台文件名；
- 四份核心文档形成双向可导航关系；
- P3 自动与手动同步契约无冲突，自动任务明确为交易日增量模式；
- SQLite 不再被描述为可排序的外部行情源；
- 新任务规范值统一为 `data_sync`；
- P0–P3 与 M1–M4 的语义明确且互不重叠；
- 所有受影响的 Markdown 相对链接有效；
- Git 差异仅包含设计稿及预定文档治理变更。
